# 咖啡店排班工具技术栈文档

## 1. 技术方案概览

本项目第一版采用静态网页应用方案。

应用部署后由用户直接在浏览器中使用，核心数据保存在本地浏览器，排班算法在浏览器内运行。项目不依赖 AI 大模型、不依赖后端服务、不需要数据库和账号系统。

推荐架构：

```text
静态网页
+ 本地浏览器存储
+ 前端 TypeScript 排班算法
+ Excel/图片导出
```

## 2. 推荐技术栈

### 2.1 应用框架

- Vite
- React
- TypeScript

选择原因：

- 适合开发静态前端应用
- 启动快，构建简单
- TypeScript 适合维护排班规则和算法模型
- 后续可平滑升级为 PWA

### 2.2 UI 和样式

- Tailwind CSS
- shadcn/ui
- lucide-react

选择原因：

- Tailwind 适合快速搭建响应式界面
- shadcn/ui 组件质量较高，可控性强
- lucide-react 适合提供清晰的工具按钮图标

### 2.3 状态管理

第一版推荐：

- Zustand

选择原因：

- 比 Redux 更轻量
- 适合管理员工、规则、时间格和排班结果
- 易于和本地存储同步

如果项目非常小，也可以先使用 React state 和 Context，但当页面拆分增多后，Zustand 会更清晰。

### 2.4 本地存储

推荐：

- IndexedDB
- idb

简化方案：

- localStorage

建议第一版可以先用 localStorage，数据结构稳定后再切换 IndexedDB。

两者区别：

- localStorage 简单，适合少量 JSON 数据
- IndexedDB 更适合较大项目数据、历史记录和导入导出

### 2.5 排班算法

第一版使用纯 TypeScript 实现。

推荐策略：

- 评分贪心生成初始排班
- 局部交换优化公平性
- 生成缺人时段报告

暂不建议第一版接入 Google OR-Tools，因为静态网页部署会变复杂。若后续规则明显复杂，可以考虑通过 WebAssembly 优化器或后端服务升级。

### 2.6 文件导出

Excel 导出：

- xlsx

图片导出：

- html-to-image

JSON 导入导出：

- 浏览器 File API

### 2.7 部署

推荐部署平台：

- Cloudflare Pages
- Vercel
- Netlify
- GitHub Pages

第一优先推荐 Cloudflare Pages 或 Vercel。

部署产物：

```text
dist/
  index.html
  assets/
```

部署方式：

1. 本地运行生产构建。
2. 将构建产物上传到静态托管平台。
3. 用户通过网址访问。

## 4. 核心模块设计

### 4.1 员工模块

职责：

- 管理员工列表
- 维护员工目标工时
- 维护员工偏好和 ban 时间

关键数据：

```ts
type Employee = {
  id: string
  name: string
  targetHoursPerWeek?: number
  preferences: Preference[]
  bans: TimeBlock[]
}
```

### 4.2 时间模块

职责：

- 生成周一至周五时间格
- 处理 30 分钟粒度
- 判断时间段重叠
- 计算班次连续性

关键数据：

```ts
type DayKey = 'mon' | 'tue' | 'wed' | 'thu' | 'fri'

type TimeSlot = {
  day: DayKey
  start: string
  end: string
}

type BusyTimeBlock = {
  id: string
  employeeId: string
  day: DayKey
  start: string
  end: string
  source?: 'manual' | 'ocr' | 'import'
}
```

### 4.3 可用时间模块

职责：

- 记录员工在每个时间格的状态
- 支持点击切换状态
- 支持批量标记

关键数据：

```ts
type AvailabilityStatus =
  | 'available'
  | 'busy'
  | 'banned'
  | 'dispreferred'
```

### 4.4 人力需求模块

职责：

- 维护每个时间段需要几个人
- 支持默认规则
- 支持用户自定义规则

关键数据：

```ts
type StaffingRule = {
  id: string
  day: DayKey
  start: string
  end: string
  requiredCount: number
}
```

### 4.5 排班算法模块

职责：

- 根据员工可用时间和人力需求生成班表
- 平衡工时公平性
- 避免违反硬约束
- 尽量满足软约束
- 输出缺人时段

输入：

```ts
type SchedulerInput = {
  employees: Employee[]
  availability: AvailabilityMap
  busyTimeBlocks?: BusyTimeBlock[]
  staffingRules: StaffingRule[]
  options: SchedulerOptions
}
```

输出：

```ts
type ScheduleResult = {
  assignments: ScheduleAssignment[]
  shortages: Shortage[]
  employeeStats: EmployeeScheduleStats[]
  score: number
}
```

### 4.6 导出模块

职责：

- 将排班结果导出为 Excel
- 将排班表 DOM 导出为图片
- 导出项目 JSON
- 导入项目 JSON

## 5. 排班算法方案

### 5.1 算法目标

在满足硬约束的基础上，最小化总惩罚分。

```text
总惩罚 =
  缺人惩罚
+ 工时不公平惩罚
+ 偏好冲突惩罚
+ 碎片班次惩罚
+ 低于最短班次惩罚
```

### 5.2 硬约束

- 忙碌时间不能排
- 忙碌时间前后各 15 分钟通勤缓冲不能排
- ban 时间不能排
- 同一员工同一时间不能重复排
- 单次班次不能短于最短连续上班时长

### 5.2.1 通勤缓冲判断

排班工具保持 30 分钟时间格，但员工课程/忙碌时间按原始区间前后各扩展 15 分钟后参与可排性判断。

判断方式使用区间重叠：

```ts
slot.start < busyEndWithBuffer && slot.end > busyStartWithBuffer
```

例如课程 `10:00-11:15` 的缓冲区间是 `09:45-11:30`。因此 `09:30-10:00` 与缓冲区间重叠，不可排；`09:00-09:30` 和 `11:30-12:00` 没有重叠，可以排。

当前 MVP 的可用时间数据仍以 30 分钟格状态保存。若未来接入 OCR/AI 课表识别，应在导入时保留课程原始起止时间，并用上述重叠规则生成或校验不可排时间格。

### 5.3 软约束

- 总工时尽量公平
- 尽量照顾个人偏好
- 尽量让班次连续
- 尽量减少碎片化排班
- 尽量靠近目标工时

### 5.4 第一版算法流程

1. 生成周一至周五所有 30 分钟时间格。
2. 根据人力需求规则展开每个时间格需要的岗位数。
3. 对每个岗位筛选可用员工。
4. 为每个候选员工计算评分。
5. 选择评分最高的员工。
6. 生成初始排班。
7. 检查低于最短连续时长的班次。
8. 尝试通过延长、替换或移除修复短班次。
9. 对工时过高和过低的员工做局部交换。
10. 输出最终排班、员工统计和缺人报告。

### 5.5 候选员工评分示例

```text
候选员工得分 =
  基础分
+ 工时不足奖励
+ 连续班次奖励
- 偏好冲突惩罚
- 接近或超过目标工时惩罚
- 造成碎片班次惩罚
```

### 5.6 缺人处理

如果某个时间段候选员工不足，算法不强行违反硬约束。

系统应：

- 保留已能安排的人员
- 记录缺少人数
- 在结果页高亮该时间段
- 在缺人列表中给出具体时间

## 6. PWA 支持

第一版可以先作为普通静态网页发布。

后续可加入：

- manifest.json
- service worker
- 离线缓存
- 添加到桌面

PWA 不是 MVP 必需项，但适合后续提升使用体验。

## 7. 不使用 AI 的原因

当前版本的核心问题是约束优化，而不是自然语言生成。

不使用 AI 的好处：

- 结果稳定
- 可复现
- 可解释
- 不需要 API Key
- 不产生模型调用费用
- 不依赖网络
- 更适合静态网页部署

AI 可以作为后续增强能力，例如：

- 课表截图 OCR
- 自然语言规则输入
- 排班结果解释
- 通知文案生成

但 AI 不应作为第一版核心排班引擎。

## 9. 质量要求

- 刷新页面后本地数据不丢失
- 排班结果不得违反硬约束
- 缺人时段必须明确展示
- 导出的 Excel 内容应与网页结果一致
- 图片导出应完整展示排班表
- 算法在 20 名员工以内应快速完成
- 界面应适配常见笔记本屏幕和手机屏幕
